Found and fixed two real bugs during implementation: (1) sidebar <nav> tag collided with the site's global 'nav' tag selector (fixed-position top navbar CSS) -- switched to a <div>; (2) showScreen() set inline style.display='block' on #admin-dashboard which overrode the new .admin-shell{display:flex} rule, collapsing sidebar+main into a vertical stack -- fixed to 'flex'. Verified live against real authenticated session again.
- (decision) Improved admin login per user request 'how could we make it easy for authorized admins to log in'. Recommended and built: (1) password reset flow via Supabase's resetPasswordForEmail + a new #admin-reset screen reached through onAuthStateChange's PASSWORD_RECOVERY event, deliberately worded to not confirm whether an email has an account (avoids enumeration); (2) passwordless magic-link sign-in via signInWithOtp, toggleable alongside password sign-in; (3) show/hide password toggle, autofocus on email field. Explicitly did NOT add Google OAuth -- requires the user to provision an OAuth app in Google Cloud Console themselves, heavier lift not needed to solve the actual gap. Security reasoning communicated to user: authentication method (password/magic-link) is separate from authorization -- the admins table + RLS gate remains the only thing that grants dashboard access, unchanged by this work. Verified all new UI states live (signin/signup/magiclink mode toggle, password visibility toggle, empty-email forgot-password validation) via DOM-only screen overrides -- deliberately did NOT submit real forgot-password or magic-link requests during testing to avoid sending real emails or creating junk Supabase Auth users.
- (decision) Security review before push, prompted by user asking directly. Caught and reverted my own over-fix: had set shouldCreateUser:false on the magic-link signInWithOtp call to stop it creating accounts for arbitrary emails, but that introduces an enumeration side-channel (Supabase returns a different error for 'no account' vs 'sent', leaking which emails are registered admins via the API response) -- the exact leak resetPasswordForEmail is designed to avoid. Reverted to the default (shouldCreateUser:true), reasoning: the 'spam an arbitrary email' capability isn't new -- the site's existing open signUp flow already lets anyone email any address a confirmation link today -- so accepting that pre-existing minor nuisance is the better tradeoff than adding a new way to probe which emails are admins.
